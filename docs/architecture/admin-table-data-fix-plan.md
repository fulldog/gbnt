# 管理后台表格数据展示修复方案

> 日期：2026-09-05。
> 基线：`main` / `01a3c43`；以当前后端字段为准。
> 状态：第一、二阶段代码已实施并通过本地回归；尚未部署或完成真实数据库联调。第三阶段数据范围规则待确认。保留仓库中已有的小程序等未提交改动。

## 1. 目标与范围

修复已复现的表格异常，并消除列表展示对系统管理权限和全量人员字典的依赖。

- 保留现有 URL、分页信封、业务字段、三态状态及台账统计口径。
- 不修改数据库业务模型，不引入原型中的额外统计列或模拟数据。
- 管理端展示扩展使用独立响应类型，不将管理端需求强加给小程序。
- 新增/变更后端接口时，同步 `apps/admin-web/src/api/` 的方法和 TypeScript 类型。
- 仅在实际改变 `/api/app/**` 契约时同步小程序 API；本方案优先保持其行为不变并补回归测试。
- 不修改只读原型，也不自动重建 `docs/api/` 下的接口文档。
- 数据范围隔离单独确认，不在表格修复中静默改变现有授权规则。

## 2. 问题、责任层与优先级

| 优先级 | 问题 | 证据/影响 | 修复责任 |
| --- | --- | --- | --- |
| P1 | 街道台账、排查汇总空结果异常 | 实测选择无记录的北城街道后报 `null.reduce`，界面保留旧记录/旧统计 | 后端稳定返回数组；前端兼容旧返回并修正异步状态 |
| P1 | 问题编号查询不到 | 实测按现有 `issue_key` 搜索为 0 条；后端仅匹配 `code/address` | 管理端后端查询条件，前端查询文案与测试 |
| P2 | 姓名、组织路径依赖额外系统接口 | 专项整改仅取前 1000 名用户；系统接口未授权、关联被删除时退化为 ID | 后端管理端响应富化；前端取消展示字典依赖 |
| P2 | 超级管理员显示“组织 #0 / 角色 #0” | 已实测；初始化超管的组织与角色 ID 为 0 | 前端依据 `is_super_admin` 和空组织语义展示 |
| P2 | 到期/逾期差一天 | 现有 `ceil((当日23:59:59 - 当前时间)/天)` 算法把今天算为 1 天、昨天算为 0 天 | 前端自然日工具及单测 |
| P2 | 旧请求覆盖新查询/查询失败仍保留旧表 | 代码未保护请求顺序；会让筛选条件与结果不一致 | 前端统一异步列表状态 |

现有有数据场景下，专项整改、组织、角色、日志及台账基础字段与后端对应。无需重做全部表格或全部接口。

## 3. 第一阶段：修复明确错误

### 3.1 台账空结果

后端：

- `LedgerStreet`、`LedgerSurvey` 的结果切片在查询前初始化为空数组。
- 无匹配记录成功返回 `data.rows: []`，不返回 `null`。
- 数据库查询失败按统一错误信封返回失败，不包装成空数据成功。
- 保留街道台账按 `org_id + type` 分组、排查汇总按 `type` 分组的当前口径。
- `pending` 继续表示 `new + pending`，`done` 继续表示 `done`；本轮不引入“每街道一行”的新聚合口径。

前端：

- 在管理端 `src/api/ledger.ts` 兼容旧服务的 `rows: null`，归一为 `[]`，页面只消费数组。
- 公开应用类型仍保持 `rows: Row[]`；临时可空类型仅用于 API 边界接收旧响应。
- 对缺失字段、错误数据类型等异常响应提示加载失败，不把所有异常都吞掉并显示 0。
- 成功空结果显示空表、总量/待处理/已整改为 0、完成率为 0%；错误结果显示错误及重试，不展示伪造的统计值。

主要位置：

- `apps/server/internal/service/issue.go`：`LedgerStreet`、`LedgerSurvey`。
- `apps/admin-web/src/api/ledger.ts`。
- `apps/admin-web/src/views/ledger/StreetLedgerView.vue`、`SurveyLedgerView.vue`。

### 3.2 问题编号搜索

- `GET /api/issues` 的 `keyword` 同时匹配 `issue_key`、`code`、`address`。
- 与类型、状态、组织子树、年度条件组合时，三个 `OR` 条件必须作为一个括号组，不能绕过其他筛选或未来的数据范围约束。
- 继续使用参数绑定，前后端统一去除首尾空白；不改变既有模糊匹配习惯。
- 前端搜索标签改为“问题编号、设施编号或地址”，新查询重置至第 1 页。
- 同步检查管理端问题/人员列表的 COUNT 错误和分页元数据：查询计数失败即返回失败；实际使用的 page/size 与回传值一致，不能得到记录却伪报总数为 0。

兼容边界：`applyIssueFilters` 同时用于管理端和小程序待办。拆出管理端专用的 keyword 条件，公共类型/状态/年度筛选继续复用；不要直接修改公共 helper，意外扩大 `/api/app/todos` 的搜索语义。

### 3.3 超级管理员与缺失关联展示

- `is_super_admin = true` 时，角色列显示“超级管理员”，不由 `role_id = 0` 推断身份。
- `org_id = 0` 显示“—”；不把超管强行绑定到某个根组织或普通角色。
- 普通账号有 ID 但关联信息不存在时，显示“组织 #ID（信息不可用）”等明确兜底，不误报为“无权限”或“已删除”。
- 保留当前超管禁止编辑、删除等行为，本阶段只改展示。

### 3.4 到期日期

采用业务自然日而非剩余小时数计算，建议统一按项目所在地北京时间（`Asia/Shanghai`）：

- 计划日期晚于今天：显示“剩余 N 天”。
- 计划日期等于今天：显示“今天到期”，不标红。
- 计划日期早于今天：显示“逾期 N 天”并标红。
- `done` 只显示计划日期，不显示倒计时或逾期颜色。
- 未填写显示“—”；非法日期安全降级，不输出 `Invalid Date/NaN`。
- 文字与行颜色使用同一计算结果。跨午夜、页面重新激活时刷新“今天”，避免页面一直打开后状态不更新。

将计算移入管理端日期工具；组件只使用派生结果，不改变后端 `plan_date: YYYY-MM-DD` 契约。

### 3.5 列表异步状态

采用轻量 composable 统一同类页面的请求顺序、加载、错误和结果更新；只抽公共请求状态，不创建大型通用表格配置系统。

- 新查询开始时保留查询参数快照，清空或隐藏旧结果及旧统计。
- 用递增请求序号保证只有最新请求能写入列表、total、error、loading。
- 旧请求迟到、旧请求失败及其 `finally` 均不得影响当前请求。
- 组件卸载后使当前请求失效；若现有 transport 支持取消可同时取消，不为此改动共享请求协议。
- 筛选和 page-size 改变时回到第 1 页；删除导致最后一页为空时退到有效页后再查一次。
- 403、网络失败与成功空结果分别展示；字典加载失败不再静默伪装成“没有选项”。

优先覆盖专项整改与两张汇总表，再应用于工作人员、操作日志和同样存在竞态的列表页面。

## 4. 第二阶段：管理端展示契约与候选数据解耦

### 4.1 为读取接口增加展示字段

保留原有 ID 字段供筛选、编辑及关联使用，新增只读名称字段：

| 管理端接口 | 建议新增字段 | 用途 |
| --- | --- | --- |
| `GET /api/issues` 的列表行、`GET /api/issues/:id` | `report_user_name`、`assignee_user_name`、`org_name`、`org_path` | 表格和详情不再全量拉取用户/组织以拼接名称 |
| `GET /api/ledger/street` 的列表行 | `org_name`、`org_path` | 无组织管理权限仍可显示已获准查看的台账组织 |
| `GET /api/sys/users` 的列表行 | `org_name`、`org_path`、`role_name` | 工作人员表不依赖角色管理、组织管理列表权限 |

字段语义：

- 姓名字段来自用户 `name`，为空时回退 `username`；仅返回展示需要的内容，不附带手机号等完整用户信息。
- 所有新增名称字段为 `string | null`。`org_path` 固定为路径字符串，例如“区 / 街道 / 村”，祖先缺失时使用可解析部分；不与节点数组混用。字段内容是当前关联名称，不承诺历史名称快照。
- 正式后端始终输出这些键，关联缺失/未设置时为 `null`。前端按原 ID 区分“—”和“信息不可用”。
- 显示已授权业务行的关联名称，不等于开放整个系统用户或组织列表权限。

后端实现：

1. 先按既有业务条件分页查询，保留原总数和排序。
2. 收集本页实际涉及的用户、组织、角色 ID，批量获取必要列；组织祖先按层批量补齐或使用受控的组织树服务。
3. 在独立管理端响应组装层补充展示字段，不为每行再执行多条人员/组织查询，不直接在分页主查询上增加会使行数膨胀的一对多关联。
4. 不为了保留旧名称绕过软删除；需要历史快照时另行确认数据模型。
5. 保留 `type_ext` 的对象形态、附件及整改记录等原响应字段。

必须处理的现有代码边界：

- `IssueVO` 自带 `MarshalJSON`，不能仅匿名嵌入它再加字段，否则新增字段可能被其序列化方法忽略。使用显式管理端序列化合并，或显式扁平 DTO，并测试最终 HTTP JSON。
- `AppGetIssue` 目前直接委托 `d.GetIssue`。扩展管理端详情前先分离 handler：小程序仍调用原基础查询，管理端调用富化查询。
- 写入接口暂不改变请求/响应。前端保存、整改、重新指派成功后重新调用管理端读取接口，不能用基础 `Issue` 响应覆盖已富化的详情。

前端类型与兼容：

- 在 `apps/admin-web/src/api/` 下定义 `AdminIssue`、`AdminIssueListResult`、管理端台账/用户扩展类型；复用公共基础类型并保持问题类型的联合类型约束。
- 不把管理端专用名称字段作为共享 `Issue` 的必填字段，不直接改小程序所用 `IssueListResult`。
- 部署过渡期允许管理端接收旧后端缺少名称字段的响应，明确降级为 ID；升级完成后以新后端必填键/可空值契约验收。
- 列表和详情一起切换到展示字段；删除 `page: 1, size: 1000` 的展示字典请求。
- 统一信封、鉴权和 Axios transport 保持不变。

### 4.2 筛选、上报人和责任人候选接口

返回行名不能代替筛选和表单候选数据。当前默认街道管理员只授权业务模块，未授权 `web.sys-org/web.sys-staff`；因此其候选查询需要随本阶段解决，不能通过给角色开放整个系统管理模块来绕过。

采用业务模块所属的轻量只读接口，以下路径已在第二阶段实施：

| 使用场景 | 建议路径/归属 | 返回与约束 |
| --- | --- | --- |
| 专项整改组织筛选及表单组织选择 | `GET /api/issues/options/orgs`，`web.rectify/view` | 最小组织树字段 `id/name/type/parent_id`；与该业务可见范围一致 |
| 新增排查选择上报人 | `GET /api/issues/options/reporters?org_id&keyword&page&size`，`web.rectify/create` | 分页返回最小人员字段；要求合法组织及对应权限 |
| 已有问题重新指派 | `GET /api/issues/:id/assignee-options?keyword&page&size`，`web.rectify/edit` | 校验编辑权限和问题存在，按该问题组织查启用人员，与当前前端的同组织候选口径一致 |
| 街道台账的街道选项 | `GET /api/ledger/street/options/orgs`，`web.ledger-street/view` | 仅街道选项与必要标识 |
| 排查汇总的街道选项 | `GET /api/ledger/survey/options/orgs`，`web.ledger-survey/view` | 同上，独立模块授权 |

- 路由可复用同一内部组织/人员查询服务，但各入口保留业务授权，不放进仅 JWT 的白名单或 `/api/app/**`。
- 候选类型独立于完整 `SysUser/SysOrg`；不包含密码、手机号等无关字段。
- 人员候选支持分页/关键字与已选人员回显，不以一次拉取 1000 人作为上限方案。
- 第二阶段只落实既有业务 RBAC、组织/问题存在性和当前候选筛选规则，不提前引入尚未确认的组织隔离。当前写入端 `Reassign` 只校验人员存在且启用，不能因下拉只显示同组织人员就宣称写入已防跨组织越权。
- 第三阶段确认数据范围及跨组织指派规则后，候选和写入同步复用统一范围服务；非法或越权目标失败关闭，不能只收紧下拉。
- 新增路由同步注册权限目录及前端 API 方法；按当前模块/action 授权机制回归已有角色。不通过重置用户自定义授权进行迁移。
- 工作人员表若需独立于组织/角色管理模块使用编辑表单，其候选能力也按同样模式归属人员创建/编辑权限；不得借名称字段绕过角色分配权限。

## 5. 数据范围隔离：独立确认项

当前 RBAC 主要控制能否调用接口，不等于按登录人的组织过滤数据。仅给前端增加街道筛选不能解决越权。

建议业务规则，需用户确认后实施：

- 超级管理员查看全部。
- 街道管理员仅查看和操作所属街道及下级村/社区。
- 村级工作人员是否允许进入管理后台、普通管理员是否具有全局范围，需明确；不能仅按角色名称或硬编码角色 ID 推断。
- 未绑定组织的普通账号默认无业务数据权限，不以 `org_id = 0` 当作全量通行证。

确认后在后端建立统一的数据范围查询/校验能力：

- 列表、工作台统计、台账、排查汇总采用一致范围；用户筛选与授权范围取交集。
- 详情、编辑、删除、整改、重新整改、指派均校验目标记录范围，不能只拦列表。
- 新增/导入逐条校验提交的组织和责任人范围；相关用户查询、导出和候选也不能成为旁路。
- 同步核查小程序对应读取/写入路径已有范围规则，避免分离 handler 后造成安全回归；如确实改变其契约或行为，另列变更并同步小程序 API/测试。
- 无权限查询返回明确错误，不把越权与成功空结果混淆。实施前先固定空范围、非法组织、跨街道 ID 的行为。

这一阶段不阻塞前两阶段的展示修复，但若业务要求组织隔离，未完成前不能宣称多街道账号可安全上线。

## 6. 验收与测试

实施前已有的 15 项管理端测试不足以覆盖这些问题，本轮针对以下场景补充回归；本地验证结果和未验范围见第 8 节：

| 场景 | 验收结果 |
| --- | --- |
| 两张汇总表全库无记录、街道无记录、日期过滤无记录 | HTTP JSON 为 `rows: []`；页面空表与零统计，无报错/旧数据 |
| 对旧服务返回 `rows: null` | 管理端兼容为空数组，页面不崩溃 |
| 查询失败或响应格式错误 | 明确错误/重试，不显示旧表或成功零统计 |
| 问题编号、设施编号、地址分别查询 | 找到正确记录；叠加年度/状态/组织时 OR 不越过其他条件 |
| 搜索小程序待办与获取小程序详情 | 原有搜索语义与 JSON 契约保持不变 |
| 仅有专项整改/台账权限，无系统人员/组织权限 | 行名与业务候选按授权正常显示；系统管理接口仍不可访问 |
| 总人员超过 1000，列表引用较早创建的用户 | 名称正确；无全量人员字典请求 |
| 管理端序列化与详情 | 新展示字段确实出现在 HTTP JSON；原 `type_ext/rectify_records` 保持兼容 |
| 关联缺失、超管组织/角色 ID 为 0 | 正确兜底；超管身份仅以 `is_super_admin` 判断 |
| 今天、昨天、明天、跨月/年、闰日、非法日期、已完成、跨午夜 | 日期文案与行颜色一致 |
| A 请求慢、B 请求快，A 随后成功或失败 | 只展示 B 结果；loading/error 不被 A 改写 |
| 筛选后分页、改 page-size、删除最后一条 | 页码和结果一致，不困在空页 |
| COUNT/聚合/关联查询故障 | 按失败处理，不制造 total=0 的成功响应 |

后端测试分服务查询测试、handler JSON 契约测试、权限测试；新增的名称关联查询应批量执行，不随列表行数线性增加。既有附件/整改记录装配的性能优化不混入本轮必做范围。

前端使用组件测试与 API 边界测试覆盖空值、错误、竞态、名称回显和日期，不只测试静态常量。联调使用隔离的测试数据，未经授权不在当前共享测试服务批量新增/删除记录。

实施后的检查命令（仓库根目录）：

```bash

pnpm --filter @gbnt/admin-web test
pnpm --filter @gbnt/admin-web build
```

## 7. 实施与发布顺序

1. **第一批：展示正确性。** 前端兼容空结果、隔离旧请求、修正日期与超管展示；后端空数组及管理端编号搜索，补定向测试。

第一批可先部署兼容旧服务的前端兜底，再部署后端修正；第二批先提供向后兼容的新增字段/接口，再启用依赖新候选接口的前端。旧字段不删除，因此旧前端仍可读取。

回滚时保留第一批前端空值保护；若回滚第二批后端，应同时回退依赖新增候选接口的前端。不能把未部署的新增接口当成线上已可用。
