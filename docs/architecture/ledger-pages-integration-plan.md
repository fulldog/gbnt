# 街道台账与街道排查汇总整合方案

日期：2026-09-06。状态：本地代码实施和自动化回归完成；未部署。真实数据库联调、容量验证及 Excel/WPS 打开验收仍待完成，详见[实施验收记录](./ledger-pages-implementation-record.md)。

配套实施规格：[两页报表实施方案与代码示例](./ledger-pages-implementation-spec.md)。本文件保留讨论确认的方向；配套文档规定契约、代码边界与验收细节。

## 1. 目标与范围

采用“一套公共报表能力＋两套业务统计＋两个独立页面”。整合重复查询、类型及页面逻辑，不合并两个页面的权限、统计口径和表格结构。

- 街道台账保留 16 列、三级表头、年度/街道/村分组合并及报表脚注。
- 街道排查汇总保留 22 个逻辑列、四层表头、左四列固定及报表脚注。
- 保留筛选、刷新、全屏、横向滚动、空态、失败重试和 Excel XML 导出。
- 后端提供扁平 JSON，前端负责表头、单元格合并和数据关联；后端不需要描述 Excel 表头。
- 本期只读，不新增资产基表、补录入口、编辑能力、签章流程或角色管理功能。
- 原型 `prototypes/static-demo/` 严格只读；不重建 `docs/api/` 或 Apifox 文档。

此前登录后的街道台账请求曾返回 HTTP 404。拆分接口不会使测试环境自动具备新路由，部署和真实认证联调是独立交付项。

## 2. 两页共用与独立边界

| 内容 | 共用部分 | 必须独立的部分 |
| --- | --- | --- |
| 组织信息 | 街道候选查询、组织祖先解析、ID/名称类型 | HTTP 入口沿用各自页面权限 |
| 筛选 | 街道及下级组织、北京时间上报日期、参数校验 | 不能把上报日期当作建设年份 |
| 分组 | 复用分组工具和稳定排序约定 | 台账按建设年份＋实际落点组织；排查按实际落点组织跨年度汇总 |
| 指标 | 缺失值规则、数据来源说明 | 建设/移交/现有指标与排查/问题/整改指标分别计算 |
| 前端 | 请求状态、行键关联、筛选、外框、导出工具 | 两张表的指标类型、表头和行合并规则 |

当前后端已共用 `loadLedgerReport`、`ledgerReportLocation` 和 `groupLedgerReport`，前端已有 `useLatestQuery`、`LedgerFilters`、`LedgerReportFrame`，应在这些基础上实施。

共用代码不等于自动减少 SQL 次数。需要验证每页请求成本，避免逐行请求统计或逐行查询数据库。

## 3. 接口方案

以下四个接口已在本地实现，不表示远端已经可用：

| 页面 | GET 基础行接口 | GET 批量统计接口 |
| --- | --- | --- |
| 街道台账 | `/api/ledger/street/rows` | `/api/ledger/street/statistics` |
| 街道排查汇总 | `/api/ledger/survey/rows` | `/api/ledger/survey/statistics` |

两类接口接收相同的 `street_org_id`、`date_from`、`date_to`，首期整表返回、不新增分页。每个页面并行请求自己的两个接口，而不是一次请求全部四个接口。

统一返回：

```text
{ code, data: { query, rows, notes }, message, cost_ms, trace_id }
```

其中 `query` 是服务端规范化后的实际筛选，`notes` 是统计口径及未知字段说明。精确默认值和字段类型见实施规格。

### 3.1 字段归属

- 基础行公共字段：`row_key`、落点组织/街道/村 ID 与名称、`natural_village`。
- 台账基础行独有字段：`project_year`、`signer`、`phone`。
- 排查基础行独有字段：`contact_name`、`contact_phone`、`leader_sign`。
- 统计公共字段：`row_key`、`source_record_count`。
- 台账统计：道路长度、林网数量、机井/桥涵闸/变压器移交和现有数量。
- 排查统计：全面排查结论、已排查设施数、正常机井数、各类问题和整改记录数。

`source_record_count` 不再混入新基础行契约；旧 `/report` 的返回结构保持兼容。未采集字段显式返回 `null`，不为了返回空资料再新增一个无数据来源的接口。

### 3.2 行键与权限

- 街道台账行键沿用 `建设年份或0:实际落点组织ID`。
- 排查汇总行键沿用 `0:实际落点组织ID`。
- 前端将行键作为不透明字符串，只在本页、本轮查询中关联；不能跨页面共享行集合或按村名拼接。
- 四个新入口分别归属 `web.ledger-street/view`、`web.ledger-survey/view`。
- 候选接口仍使用本页入口，内部共用查询，避免跨页面权限耦合。
- 不将现有模块查看权限描述成已经具备用户组织数据隔离；本期不扩大授权范围或另外设计组织权限。

## 4. 后端改造

1. 抽取公共查询校验、过滤、位置解析和排序；基础行仅查询分组/位置所需列，统计接口读取计算所需列。
2. 保留台账指标和排查指标两个计算模块，复用现有已验证的统计规则，不复制两套公式。
3. 增加路由、中文 DTO 注释及 API 注册目录条目，沿用本页查看权限。
4. 旧 `/street`、`/survey` 和两个 `/report` 暂时保留。旧 `/report` 与新入口复用同一套底层业务函数，但不通过 HTTP 自调用组装。
5. API 未匹配路由、参数错误和查询失败统一返回 JSON 信封，不把失败伪装成空数组成功响应。
6. 新增接口时，同阶段同步管理端正式方法、参数和响应类型。

## 5. 前端改造

1. 管理端增加四个 API 方法和相应的基础行/统计行类型。业务类型留在管理端，不放入两端共享业务包。
2. 增加纯函数：验证筛选、校验行键唯一性和集合一致性、按键关联、按基础行顺序输出、合并口径说明。
3. 在现有 `useLatestQuery` 上封装薄的报表 composable，统一请求编排；不重写请求序号和页面销毁保护。
4. 复用 `LedgerFilters`、`LedgerReportFrame` 和导出工具；保留 `StreetLedgerSheet`、`SurveyLedgerSheet` 的差异。
5. 两个接口均成功且校验通过后，一次性提交页面数据。任一失败或行集合不一致则清空旧数据、显示错误、禁用导出。
6. 街道候选与报表分别加载和重试。快速切换筛选后，旧请求不得覆盖新结果。
7. 标题、日期说明和导出使用已成功查询的数据及筛选，不使用尚未点击查询的表单草稿。

共享请求核心一并区分非标准 404、网关错误和成功响应格式错误；合法信封优先显示后端消息，保留鉴权失效、Token 续期、Trace ID 及原始下载响应语义。

## 6. 数据准确性边界

- 合法 `null` 表示未采集或无法可靠计算，显示 `—`；实际为零才显示 `0`。
- 缺少字段、缺少统计行、重复键、额外统计行是契约错误，不等于合法 `null`。
- 继续按筛选后实际存在的上报记录产生报表行，不用整棵组织树生成虚假的“零台账”。
- 道路/林网为上报记录字段合计，不是去重资产总量；问题/整改是当前记录口径，不是历史事件累计。
- 没有资产基表和完整采集来源时，设施总量、自然村、全面排查结论及报表资料保持未知。
- 联系人、签字字段含义不同，不因都是姓名或电话就默认同一个人。

双请求并行与前端一次性更新只避免半份报表展示，不保证数据库同一快照。行键一致也检测不到同一行指标在两次查询之间的变化。首期按实时查询验收；正式签章报表需要另行设计真实快照或具备一致读取语义的单请求聚合，不能用 `trace_id`、`generated_at` 或相同日期冒充快照凭据。

## 7. 实施与验收

顺序为：字段与用例冻结 → 后端接口＋前端方法同步 → 前端组合 → 通用错误处理 → 自动化测试 → 后端部署 → 前端切换 → 真实联调。

至少验证：

- 独立固定测试数据的人工预期，以及新组合结果与旧 `/report` 的兼容性；旧接口不能作为唯一正确性依据。
- 跨年度、同名不同组织、缺失组织关联、缺失年份、日期边界、空数据、`null/0`。
- 重复/缺失/额外统计行、任一接口失败、快速筛选、组件销毁后返回。
- 16/22 列、三级/四层表头、行合并、固定列、滚动、全屏、导出与筛选一致。
- 后端测试、管理端类型检查/测试/构建；共享请求层改动后回归小程序。
- 登录后四个新接口返回 HTTP 200 且 `code: 0`，并用可核验的真实样本验证指标。

部署前备份并检查数据库配置。当前代码在 `migrate.enabled=true` 且 `server.mode=debug/dev` 时启动会删表重建；测试环境有数据时不得这样启动，应确认 `release` 并审查迁移。

合入远端 `ebe0f15` 后，即使 `migrate.enabled=false`，启动仍会写入同步 `sys_apis` 并加载权限索引；应检查表结构、数据库写权限和执行结果，不将关闭迁移理解为只读启动。
