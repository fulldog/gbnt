# 设施编号方案调整：提交时分配与重复校验

日期：2026-09-10。状态：三端代码已按修订方案实施，本地测试及隔离环境验收完成；尚未迁移业务库或部署。

本方案替代之前“填写时预填条数加一、允许重复”的方案。旧建议编号接口和前端查询联动已经移除。

## 1. 业务口径与适用边界

本版暂按原需求“一条巡查工单使用一个编号”的口径设计，编号仍保存在 `issues.code`，不新增设备档案。

本轮按用户确认实施的一单一号口径落地。如果以后要求同一设备多次巡查沿用原编号，应另行建立“设备档案编号唯一、多条巡查关联同一个 facility_id”的模型。业务库迁移前仍须核对历史重复的含义。

本版采用以下规则：

- 默认自动编号，填写和保存草稿时不生成正式编号、不创建工单、不占号。
- 点击提交后，由后端在保存工单的同一事务内分配编号；只有事务提交成功，编号才正式生效。
- 用户可以切换为手动填写；手动编号重复时阻止保存，不能只警告后继续提交。
- 唯一范围为“所选组织 ID + 设施大类 + 规范化编号”。不同村可以同号，同村不同类型也可以同号。
- 所选组织按精确 `org_id` 判断，不合并下级；类型为 well/road/bridge/forest/transformer，不按子类型区分。
- 同一范围内跨年份、状态、上报人、小程序/后台来源一起计数和查重；整改记录与整改轮次不计入工单条数。
- 已软删除工单不参与计数和占号；因此删除后可能再次用到旧号码。本版不承诺历史永久不复用。

## 2. 自动编号算法

保留原需求的“工单条数加一”作为起点，增加跳过占用号码的步骤，不改成取最大编号加一：

1. 在事务及组织锁内，统计所选组织、同类型未删除工单条数 N。
2. 从 N + 1 开始，生成至少两位的十进制编号。
3. 该编号已被占用则继续递增，直到找到可用编号。
4. 将最终编号与当前工单一起写入并提交事务。

| 现有有效工单编号 | 工单数 | 自动分配结果 |
| --- | ---: | --- |
| 无 | 0 | 01 |
| 01、02 | 2 | 03 |
| 01、03 | 2 | 04，跳过已占用的 03 |
| 01、08 | 2 | 03，保持按条数起步 |
| 01 至 99 | 99 | 100 |

遗留空编号记录仍是工单，参与条数统计，但空编号不占具体号码。手动编号可以跳号，之后自动分配仍采用上述算法。

## 3. 并发与数据库实现

### 3.1 保存事务

自动分配和手动保存共用后端服务，所有新增入口（包括导入）必须复用该服务：

1. 校验登录、权限、组织、当前页完整性及附件；附件上传不放进编号事务。
2. 开启短事务，锁住所选 `sys_orgs` 行，再进行编号相关读写。第一版复用组织行锁，同村不同类型暂时也会顺序执行，无需新增序号表。
3. 事务采用 READ COMMITTED，保证锁获取后计数和查重能读取先前事务已提交的结果。
4. 自动模式计算可用编号；手动模式规范化后查重。
5. 写入工单，提交后返回真实 `id`、`issue_key` 和 `code`。

组织锁只覆盖保存的短时间，不从进入填写页面开始持有。MySQL 官方说明，普通 SELECT 后再写入不足以防止并发竞争，应使用事务内的锁定读取。[锁定读取与编号分配示例](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

例：A、B 同时新建 A 村道路，已有两条工单。先提交的事务得到 03，后一个事务读取更新后的数量，得到 04。A 仅填写未提交不会影响 B。

### 3.2 数据库唯一约束

- 除服务层校验外，增加未删除工单的 `(org_id, type, active_code_key)` 联合唯一索引。
- `code_key` 保存统一规范化结果，所有创建、编辑、导入路径都由后端计算，客户端不能指定。
- `active_code_key` 为生成列：有效非空编号取 `code_key`，软删除或历史空编号取 NULL。唯一索引允许多个 NULL，从而不让多个已删除历史版本互相冲突。[MySQL 唯一索引规则](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)
- 不直接使用 `(org_id, type, code, is_delete)` 唯一索引；删除标记只有 0/1，多次删除同号记录会产生历史行冲突。
- 数字编号统一比较：例如 1、01、001 视为同号，显示为 01；100 显示为 100。非纯数字保留现有手填能力，去首尾空白，比较规则与后端规范化保持一致，使用显式排序规则消除环境差异。
- 仅把设施编号唯一索引冲突转为“设施编号重复”；不得把 IssueKey 冲突或其它数据库故障误报为编号重复。
- 自动分配遇到并发冲突或死锁时，有限次数重试整个事务并重新读取，不重试旧快照上的单条插入；手动冲突不偷偷更换号码。

### 3.3 编辑、删除、导入

- 编辑时默认保留原编号，不自动重新分配；查重排除当前工单 ID。
- 修改组织或类型时，即使 code 没变，也必须按新的组合重新查重。
- 保留 `expected_updated_at` 编辑冲突保护；它与编号查重是两种不同错误。
- 涉及多个组织的编辑按组织 ID 固定顺序加锁，配合行锁及有限事务重试，避免锁顺序混乱。
- 删除释放有效编号的占用；删除入口遵守相同锁顺序。当前没有恢复入口，如以后新增恢复，恢复时同样查重。
- 导入仍复用现有逐行创建、遇错停止的语义；已导入的前序行不伪装成回滚。重复错误提示第几行、已成功几条，避免用户误以为整批均未保存后重复导入。

### 3.4 重试与重复提交

创建接口支持 `request_id`：新客户端为一次提交生成并保存固定请求 ID，网络重试复用；后端在同一事务中登记并以唯一约束防止重复创建，成功重试返回原工单和原编号。导入文件每行有独立请求 ID，同一已加载批次重试时复用。

请求 ID 要绑定当前操作账号与提交内容；相同 ID 对应不同内容时返回明确冲突，不能返回别人的记录。事务失败时登记一起回滚。成功后重读详情失败不能让客户端误以为工单未保存而重新建单。

这解决的是同一次提交被重试的问题；组织锁和编号唯一索引解决的是不同人员同时提交的问题，两者分开验证。

## 4. HTTP 与共享契约调整

优先修改现有保存接口，不新增“提前占号”接口：

| 接口 | 调整 |
| --- | --- |
| POST /api/app/issues | 增加 code_mode，自动模式由后端生成，手动模式查重 |
| POST /api/issues | 与小程序使用相同编号规则，保留管理端创建权限 |
| PUT /api/issues/:id | 编号/组织/类型变更时检查最终组合，排除自身 |
| POST /api/issues/import | 每行复用创建规则，返回可识别的失败行及已成功数量 |

创建字段：

| 字段 | 语义 |
| --- | --- |
| code_mode | auto 或 manual；新版客户端必须明确传递 |
| code | auto 不传具体编号；manual 必填，后端规范化及查重 |
| request_id | 同一次提交重试保持不变；新客户端携带，兼容旧客户端省略 |

向后兼容：旧客户端省略 code_mode 时，非空 code 按手动处理；空 code 按自动处理。明确 manual 但空编号报 400，不能暗中切到自动。非法模式、auto 同时带入非空 code 都报参数错误，避免误解用户意图。

成功仍使用现有 `{ code, data, message, cost_ms, trace_id }` 信封，`data.code` 是已保存的真实设施编号。客户端不在成功后自行计算或再次补写。

重复编号返回 HTTP 409、业务码 40901，沿用现有错误信封。提示：“当前组织该类型设施编号已存在，请修改或使用自动编号。” 重复请求内容冲突使用 40902，原有编辑版本冲突保持原有业务码。

现有 ApiError 已支持数字业务码，两端可据此定位设施编号字段，无需依赖匹配中文提示文本。

共享包同步两端创建 DTO、编号模式及冲突码；管理端和小程序各自的 API 方法按对应路径同步。共享包不引入 Vue、Axios、uni 或 DOM。

## 5. 小程序调整

- 编号区域默认选中“自动生成”，展示“提交时自动生成”，不展示临时数字。
- 提供“手动填写”入口；切换后出现可编辑输入框。另设明确的“恢复自动生成”操作。
- 自动模式允许 code 为空，完整性校验不再拦截空编号；手动模式仍校验必填。
- 每个类型独立保存 codeMode 与手动输入，切换类型继续静默保存，提交只校验和发送当前类型。
- 用户主动清空手动编号仍保持手动模式，提交时提示必填；不得因为空值而覆盖为自动模式。
- 切换组织不再请求建议号；自动模式仍保持自动，手动内容保留，由提交时按最终组织校验。
- 旧草稿非空编号保守迁移为手动；空编号迁移为自动。明确标记为旧建议值的 codeSource=auto 可迁为自动，旧值不作为最终编号提交。旧 codeSource=manual 的空值仍保留为手动空值。
- 编号模式、手动内容的实际修改沿用现有签名失效处理；恢复同一份草稿、切换隐藏不重复清签名。
- 收到重复错误时保留当前表单、照片和签名笔迹，显示编号错误并引导返回基本信息。只有提交成功才清理当前类型草稿。
- 使用返回的真实编号展示提交结果；不再依赖 useFacilityCodeSuggestion 或任何计数响应来填写 code。

## 6. 管理后台调整

- 新增表单使用与小程序相同的“自动生成 / 手动填写”两种模式。
- 新增时切换类型保留各类型手动输入；自动模式不发建议编号请求。
- 编辑表单始终回显已保存编号，不默认切入自动编号；用户可手改，组织/类型变化后也会校验最终组合。
- 编号冲突在该字段附近提示，弹窗和其它输入保持不动。
- 导入同步创建契约和重复错误展示；保留已有的逐行提交语义。
- 列表、详情、导出继续读取服务端 code，不在前端补号。

## 7. 历史数据与发布顺序

以前允许重复，因此不能假设现有数据满足唯一索引。本轮尚未连接业务数据库，也没有声称已查明存在或不存在重复。

1. 提供只读审计，输出精确组织、类型、原编号、规范化编号、涉及工单 ID；覆盖普通重复、1/01 等规范化重复、空编号和已删除记录。
2. 如果重复记录实际属于同一设备的多次巡查，应回到第 1 节采用设备档案模型，不能擅自把它们改成不同设备。
3. 如果确定是一单一号，对确有冲突的历史记录提供具体处理清单。历史改号属于业务数据变更，需在清单可审阅后再执行，不自动重编号。
4. 在受控发布窗口暂停相关写入，完成规范化键回填、重复复核和唯一索引建立；不把未通过审计的索引变更直接塞进启动 AutoMigrate。
5. 部署兼容旧客户端的新后端并同步权限目录，确认没有旧服务实例绕过 code_key 写入，再恢复写入。
6. 发布后台与小程序；旧客户端仍能通过 code_mode 兼容规则提交，但也会受到唯一性校验。

不在持续运行的业务库上使用 debug/dev 启动或重建数据。迁移失败时保持明确错误，不自动删数据、改号或取消唯一约束。

## 9. 验收清单

- 0/2/99 条记录分别生成 01/03/100；已有 01、03 时生成 04，已有 01、08 时生成 03。
- 填写未提交、保存草稿、切换类型均不增加数据库记录，也不占用号码。
- 同村同类型两个自动提交得到不同号码；两个相同手动号仅一个成功；手动与自动竞争也不重复。
- 同号跨村或跨类型允许；同村同类型跨年份、状态、上报来源仍拦截。
- 1、01、001 按同号处理；手动冲突、数据库故障和其它唯一键冲突分别正确提示。
- 创建失败事务回滚；同一次提交网络重试不创建第二张工单；成功返回真实已保存编号。
- 编辑不改编号时不误报自身重复；只改组织或类型也能识别目标范围的冲突。
- 多次删除并重用同号不发生已删除历史行唯一冲突；删除后的计数和占用释放符合口径。
- 导入撞号、已有历史重复、迁移重跑均有明确结果，不能静默改号或重复导入前序成功行。
- 自动模式不因空编号阻止提交；手动清空保持空值；旧草稿迁移、切换类型、错误返回都不丢内容。
- 新旧客户端兼容、两端鉴权、权限目录和 DTO 同步有测试；运行 Go 测试、三包类型检查、两端测试及构建。
- 使用隔离 MySQL 的真实并发连接验收事务和唯一索引；SQL 查询桩不能代替并发验收。
- 后台浏览器及微信开发者工具检查编号模式和错误回显，涉及已有签名/照片/定位链路时补真机回归；未执行的验收明确列出。
