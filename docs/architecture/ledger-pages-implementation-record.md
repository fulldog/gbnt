# 两页报表实施与验收记录

日期：2026-09-06。

依据：[整合方案](./ledger-pages-integration-plan.md)、[实施规格](./ledger-pages-implementation-spec.md)。

结论：本地实现和自动化回归完成，两张表已在浏览器使用固定黄金数据验收。首次实施验收时没有部署、操作真实数据库或提交推送 Git；后续用户已授权拉取、合并和推送，Git 操作结果以对应任务回执为准，不宣称测试环境新接口已经可用。

## 1. 已实施内容

- 后端新增四个 GET：`/api/ledger/street/rows`、`/api/ledger/street/statistics`、`/api/ledger/survey/rows`、`/api/ledger/survey/statistics`。
- 两页各自保留原 module/view 权限和候选接口；旧聚合与 `/report` 方法保持兼容。
- 新接口统一严格校验 ID、日期、未知/重复参数及 URL 编码；返回规范 query、非 null 数组和统一响应信封。
- 基础行只读取去重的 `org_id/project_year`（排查汇总仅 `org_id`），不读取 `type_ext`；统计批量读取并计算。两条路径复用组织、日期、软删除过滤与分组能力。
- `source_record_count` 仅由统计接口提供。资产总量、自然村、联系人和签字等未采集信息仍为 null，不用上报条数冒充资产数量。
- 管理端四个正式 API 方法、TypeScript 类型及严格解码器同步完成。白名单明确字段归属，不让额外字段覆盖另一供数方。
- 新增纯合并方法和薄 `useLedgerReport`：并行发两次请求，按 row_key 关联；筛选不符、缺行、额外行、重复键均整组失败。复用 `useLatestQuery` 的请求序号和销毁保护。
- 保留两张独立 Sheet、Frame、CSS、合并格和固定列。导出按钮与事件处理函数均校验状态；标题、日期说明及文件名基于成功提交的筛选。
- 共享请求核心区分非标准 404、502/503/504 等 HTTP 错误与 2xx 格式错误；保留业务消息、登录失效、续期响应头、Trace ID 以及 raw 下载语义。
- 后端仅对 `/api` 或 `/api/` 前缀接入统一 NoRoute；不绕过原 JWT/RBAC，不覆盖已 Abort 的错误响应。

## 4. 性能观察及边界

- 每页固定两次供数请求，候选请求独立；每个供数接口两次业务 SQL（组织＋基础 DISTINCT 或批量记录），每页共四次业务 SQL。不含 JWT/RBAC 可能产生的额外查询。
- `BenchmarkLedgerParts10k`：Apple M2 Pro，1 万条记录、100 个模拟落点组织，对两页统计进行纯分组、计算与 JSON 序列化，运行 3 次；约 28.4 ms/op、27,326,632 B/op、234,054 allocs/op，序列化后的两页统计数组合计 80,276 B。
- 上述内存数字是累计分配，不是峰值驻留内存；返回体不包含基础行、信封及 HTTP 开销。该基准不是实际数据库延迟、HTTP 压测或大表浏览器容量结论。
- 本期不分页、不缓存、不静默截断。发布前仍应使用有代表性的真实组织/记录规模测量端到端延迟、内存和完整响应体。
- 双请求不共享数据库快照；键不一致能够被发现，同键集合内的实时指标变化不能被检测。正式盖章快照仍须另行设计。
