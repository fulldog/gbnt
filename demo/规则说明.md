# 高标农田专项整治平台 · 规则说明

> 栈 B 演示版业务规则汇总。实现代码以 `frontend/js/well-submit-rules.js`、`well-water-photos.js` 等模块注释为准；本文件供产品、后台与移动端联调对照。

---

## 一、问题状态（三态）

| 状态值 | 展示名 | 含义 |
| --- | --- | --- |
| `pending` | 待整改 | 存在问题，须整改责任人处理 |
| `done` | 已整改 | 责任人已提交整改结果与照片 |
| `inspected` | 已排查 | 现场排查无问题，**不需要**进入整改流程 |

### 状态流转

```text
巡查提交（末步须电子签名 · 与最终状态无关）
    ├─ 排查无问题 → inspected（已排查）
    └─ 排查有问题 → pending（待整改）
                         ↓ 责任人提交整改反馈（说明 + 照片 · 无签名）
                    done（已整改）
```

- **已排查**：仅记录与归档，**不**进入任何人的「待整改」待办。
- **待整改**：按区划推送给**整改责任人**，出现在其移动端「待办」列表（按手机号 / 人员 ID 匹配）。
- **已整改**：原「待整改」项在责任人提交**整改反馈**（说明 + 照片）后变为已整改；**无**整改电子签名、详情**不**再展示单独「整改措施」板块。

### 已排查判定（与是否签名无关）

选项只决定 `inspected` / `pending`，**不**决定要不要签名页。

| 题目类型 | 算「无问题」的答案 | 示例 |
| --- | --- | --- |
| **正向题** | 「是」 | 机井六题、路肩、灰土层、通电、设备完好… |
| **反向题** | 「否」 | 林网断带/枯死木/病虫害、变压器私拉乱接、**桥涵闸是否需要整改** |

全部无问题 → `inspected`；任一项有问题 → `pending` + 自动指派整改责任人。

## 二、机井巡查提交 · 状态判定

适用：**移动端机井分页向导**（填写页 → 单选题×6 → 电子签名 → 提交）。

### 单选题顺序

1. 机井是否出水（≥5分钟）
2. 管道是否按要求连接
3. 走线是否规范
4. 配电箱及电表等设施是否完好
5. 井台、井盖是否完整
6. 变压器是否正常使用（位置复用现场地址 / 定位；选「否」须描述+照片）

### 判定规则

- **全部为「是」** → `status = inspected`（已排查）；不指定整改责任人。
- **只要有一项为「否」** → `status = pending`（待整改）；须指定整改责任人并推送待办。

实现：`AppWellSubmitRules.evaluateWellQuiz(wellQuizData)`

## 三、整改责任人指派

### 指派原则

- 仅当状态为 **待整改** 时指派。
- 责任人对应**最下级行政区划**：
  - 若上报选择了 **自然村** → 匹配该自然村（组织树节点）的工作人员；
  - 若无自然村 → 匹配 **村/社区** 的工作人员。
- 人员在**管理端 · 系统配置 · 工作人员**中维护，按所属单位（组织）挂接。
- 同一单位多人时，优先 `rectifyAssignee: true` 标记的账号；否则取该单位第一条启用人员。

### 推送（演示）

- 演示环境：**不**真实发短信；提交后写操作日志，记录「推送整改待办」及责任人手机号。
- 正式环境：由后台按 `assigneePhone` 调用短信/消息服务（本仓库栈 B 不实现）。

实现：`AppWellSubmitRules.resolveAssignee({ street, village, naturalVillage })`

### 待办可见范围（移动端）

- **待整改**且当前登录人手机号 / 人员 ID / 姓名与 `assigneePhone` / `assigneeId` / `assigneeName` 一致 → 出现在其「待办」。
- **已排查**不进入责任人待办。
- 管理员账号可见全部待办（演示）。
- 清单/台账等**组织范围数据**另见第四节「组织数据权限」。

## 四、组织数据权限

按**组织树层级**控制可见范围（概念规则；栈 B 演示可不做强校验，正式环境由后台按人员所属单位落地）。**不做**人员级「只能看自己上报的单」——同单位内同事可见本单位范围内数据。

| 规则 | 说明 |
| --- | --- |
| **上级可看下级** | 所属单位为上级节点时，可见其全部下级单位（含再下级）范围内的清单 / 台账 / 人员等相关数据 |
| **同组织可看** | 同一单位节点下的工作人员，相互可见本单位范围内的数据 |
| **平级跨组织不可看** | 无隶属关系的同级单位之间（如甲街道 ↔ 乙街道、甲村 ↔ 乙村）**不可**互看对方数据 |
| **下级不能看上级** | 所属单位为下级节点时，**不可**看上级单位或其他兄弟分支的数据；仅本单位及（若有）自身下级 |

### 示例（示意）

```text
管委会          → 可见全树
 └─ 蒋官屯街道  → 可见本街道及下辖村/社区/自然村；不可见东城、北城
     └─ 李官屯新村 → 可见本新村及下辖自然村；不可见同街道其他新村/社区，亦不可见街道本级汇总之外的「上级专属」视角
         └─ 蒋官屯村 → 仅本自然村；不可见李官屯新村本级及其他自然村
```

与「整改责任人待办」的关系：待办推送仍按第三节指派匹配；组织权限决定**能浏览哪些单**，责任人匹配决定**谁须处理待整改**。

## 五、机井「是否出水 = 是」· 现场取证（全项目唯一特殊）

模块：`frontend/js/well-water-photos.js`（`AppWellWaterPhotos`）

| 规则 | 说明 |
| --- | --- |
| 触发条件 | 仅「机井是否出水」选 **是** |
| 张数 | 至少 **2** 张 |
| 来源 | **仅摄像头**，禁止相册上传；点击「+」直接请求摄像头 |
| 水印 | 每张入库前烧录水印（地址 + 坐标 + 时间） |
| 间隔 | 以第一张水印时间 `firstCapturedAt` 为准，须 **≥2 分钟** 后才可拍下一张 |
| 倒计时 | 第一张提交后，添加位显示 **MM:SS** 倒计时，结束才可继续拍 |
| 数据 | `wellQuizData.waterOut.photoProof.firstCapturedAt` |

选「否」时走普通照片条（可拍照/上传），无上述限制。

## 六、电子签名（排查要、整改不要）

模块：`frontend/js/mp-signature.js`（`AppMpSignature`）  
客户约定：**排查需要签字；整改不用。**

| 环节 | 是否须签 | 说明 |
| --- | --- | --- |
| **排查上报**（移动端巡查向导 / 管理端新增·编辑巡查） | **须** | 各类型（机井 / 道路 / 桥涵闸 / 林网 / 变压器）选项页走完后**固定**进入电子签名步；须签完才可提交。**不**根据中途选项、也**不**根据最终会变成「已排查」还是「待整改」来显隐签名 |
| **整改闭环**（移动端详情「整改反馈」） | **不要** | 仅填写说明 + 上传整改后照片；**无**签名画布 |
| **详情展示**（移动端巡查详情 / 管理端左栏「整改前」） | 有则显 | 展示字段 `reporterSignature`（上报人排查签名）。待整改 / 已整改 / 已排查均可有签名——签的是**排查上报**，不是整改责任人 |

- 签名保存为 PNG DataURL，字段：`reporterSignature`。
- 代表**上报人**本人确认排查内容。
- 实现：移动端 `m-report.js`；管理端 `report-form-engine.js`（右栏签名）；整改提交 `m-issue-detail.js`（无签名）。

## 七、选项页校验（全类型统一）

适用：机井 / 道路 / 林网 / 变压器 / **桥涵闸**等所有带单选题的分页向导。

### 何时必填「问题描述 + 现场照片」

须在**当前选项页**完成，才可点「下一步」；**不在**签名提交页才校验。

| 题目类型 | 示例 | 须描述+照片的答案 |
| --- | --- | --- |
| **正向题**（是=正常、否=有问题） | 是否有路肩、是否通电、管道是否连接… | 选 **「否」** |
| **反向题**（是=有问题、否=正常） | 林带是否断带、**是否有枯死木**、是否病虫害、是否私拉乱接、**桥涵闸是否需要整改** | 选 **「是」** |

- 表明**无问题**的一侧（正向题选「是」、反向题选「否」）：备注选填，**不要求**照片。
- 表明**有问题**的一侧：**描述必填** + **至少 1 张**现场照片（可拍照或上传）。
- 机井「是否出水 = 是」：仍走第五节出水取证（摄像头两张），不重复此表。

实现：`m-report.js` · `quizAnswerIndicatesIssue` / `validateQuizStepBeforeNext`

### 反向题清单

- **林网**：`brokenBelt` 断带、`deadTrees` 枯死木、`pest` 病虫害
- **桥涵闸**：`needsRectify` 是否需要整改
- **变压器**：`illegalWire` 私拉乱接

## 八、道路巡查提交 · 状态判定

适用：**移动端道路分页向导**（填写页 → 单选题×2 → 电子签名 → 提交）。

### 填写页

区划、项目年度、编号、长度 / 宽度 / 厚度、林网存活率、整改计划日期、定位。**无**问题描述、现场照片、负责人/电话。

### 单选题

1. 是否有路肩
2. 是否有灰土层

### 选项页照片

- 可 **拍照或上传**（`AppMpPhotos`），**无**机井出水题的摄像头-only / 2 分钟间隔限制。
- 校验规则见上文 **第七节「选项页校验」**。

### 判定规则

同机井三态：全「是」→ `inspected`；有「否」→ `pending` + 推送整改责任人。

实现：`AppWellSubmitRules.applyRoadSubmit(quizData, region)`

## 九、其他机井向导约定

- 填写页：区划、项目年度、编号、设施类型、出水口/护筒数量、整改计划日期、定位。
- 单选题：存在问题须本页描述+照片（正向题「否」、反向题「是」如枯死木）；无问题侧备注选填（出水题除外见上表）。
- 整改责任人/联系电话/井长**不在上报端填写**，由后台区划配置或提交规则自动指派。
- 进度条总步数：**8**（填写 + 6 题 + 签名），末步 100%。

## 十一、管理端专项整改列表 · 默认排序

适用：`web/rectify.html` 巡查清单（筛选后、分页前）。实现：`frontend/js/pages/rectify.js` · `sortIssues`。

### 分组优先级（自上而下）

| 顺序 | 分组 | 判定 |
| --- | --- | --- |
| 1 | **逾期** | `status === pending` 且相对 `planDate` 已逾期 |
| 2 | **待整改** | `status === pending` 且尚未逾期 |
| 3 | **已整改 / 已排查** | `status === done` 或 `inspected`（两组同级） |

### 组内排序

| 分组 | 规则 |
| --- | --- |
| 逾期 | **逾期天数大的在前**（天数相同时再比小时分量） |
| 待整改 | **剩余天数大的在前**（天数相同时再比小时分量） |
| 已整改 / 已排查 | 按**最新业务时间倒序**：已整改取 `rectifyAt`（无则 `createdAt`）；已排查取 `inspectionDate`（无则 `createdAt`） |

### 天数依据

- 以 `AppData.planRemain(planDate)` 为准（相对计划完成日 23:59:59）。
- 无有效 `planDate` 的待整改项：归入「待整改」组，天数权重按 0 处理，再按最新时间倒序兜底。

### 列表展示相关（同页约定）

- **行政区划**：`街道 + 村/社区 + 自然村`（有自然村须拼到第三级），不省略。
- **计划完成**：`YYYY年MM月DD日`；已排查显示「—」。
- **逾期行**：浅红底；倒计时文案红色。
